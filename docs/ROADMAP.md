# 功能规划（Roadmap · 含需求分析与优先级建议）

> 更新：2026-09-03 · 状态：**规划中，尚未开发**。
> 本文档把口述需求拆解为可评估的功能项，给出建议优先级与分期路线；
> 优先级为产品向建议，可随时调整，**原编号顺序不代表优先级**。

---

## 一、需求分析与拆解

口述的 11 条诉求，按产品逻辑归类后其实是三类：**体验层**（立竿见影的观感/上手）、
**平台层**（账号与数据地基）、**生态层**（观战、管理、运营）。逐条分析如下：

| # | 功能 | 分析（要点 / 隐含问题 / 建议边界） | 影响模块 | 前置依赖 |
|---|------|------------------------------------|----------|----------|
| 1 | 悔棋 | 三种对局模式规则不同：本地双人可任意悔；人机可悔；**在线必须防滥用**（建议"请求悔棋→对方同意"，并限制次数）。技术核心是**整步快照回滚**（含夹/挑连锁结果），需记录每步前的棋盘+行棋方。 | 前端状态机 / shared 逻辑 / 在线协议 | 无（在线版需要 #10 前的服务端状态栈） |
| 2 | 第三方旁观 | 需"只读观众"连接：不占 2 人位、可中途进入看到**当前局面**、实时跟进每一步。隐含需求：**房间入口**（房间列表 / 邀请链接 / 房间码搜索）。为 #4 复用同一套广播基建。 | 在线协议 / 房间模型 / UI 房间列表 | 服务端房间快照与历史缓冲（可与 #5 同源） |
| 3 | 新手教程 | "首次进入走一遍规则 + 后续可再学"建议做成**可交互引导**（演示→跟走→自由试），首次判定可用本地标记，登录后可按账号记忆（#9）。注意 web/桌面/小游戏三端内容一致性问题。 | 前端 UI / 规则引擎复用 | #7 特效组件可共用 |
| 4 | 管理员功能 | 前提是**可信的身份角色**（#9），不能只靠前端隐藏。能力建议分档：先"只读进入所有房间实时观棋"（复用 #2），再评估"踢人/封禁/终止对局"。独立管理页 + 操作审计（配合 #10）。 | 鉴权 / 服务端权限 / 管理 UI | #9 + #2 + #10(审计) |
| 5 | 历史记录 | 记录**在线房间对局**为主（本地对局默认不落库，可选项）。每局需保存：双方身份、起止时间、胜负方式、房间号、**完整走子序列**。走子序列正是 #6 回放的数据源，两者必须一起设计数据格式。 | 数据层 / 列表页 | #10（DB）+ #9（归属） |
| 6 | 回放 | 播放走子序列的动画（前端现有连锁动画可复用），支持步进/变速/跳转/终局视图。建议定义统一对局记录格式（元数据 + 走子 + 结果），先与 #5 共用。 | 前端播放器 / 数据格式 | #5 + #10 |
| 7 | 吃子特效优化 | 现有"灰闪 + 音效"偏朴素。方向：分**夹/挑/连锁**不同反馈、粒子/震屏/连击感、音效分层、可开关（动效偏好）。纯前端 Canvas 打磨，成本可控、感知最强。 | 前端渲染/音效 | 无（独立小迭代） |
| 8 | 自定义头像与昵称 | 拆两期：先做**本地资料**（游客也能改，存本地/浏览器），#9 后做**云端资料**（登录可见、跨设备）。头像建议先预设库/Emoji，开放上传放后期（需审核/存储）。昵称需长度与敏感词约束。 | 前端 UI / 用户资料 | 本地版：无；云端版：#9 + #10 |
| 9 | 登录 + 游客模式 | 游客体验很关键：自动游客身份 + 一键"升级为账号"（保留历史与资料）。登录方式建议**免密优先**（验证码/微信/三方），密码为辅；服务端会话与安全是硬要求。此功能是 #4/#5/#8 的身份地基。 | 鉴权 / 会话 / 数据归属 | 无（但建议与 #10 一起排期） |
| 10 | 数据库持久化 | 承接全部"记录类"需求（#5/#6/#8/#9/#4 审计）。选型建议：**SQLite 起步**（单文件、零运维、易备份）+ 数据访问层抽象（后续可迁 PostgreSQL）；需建迁移机制、备份策略，并同步进 deploy.sh/update.sh。 | 服务端数据层 / 部署 | 无（与 #9 组成平台地基） |
| 11 | 亮 / 暗双主题 | 现状"墨夜鎏金"为暗色，需再补**亮色主题**并提供切换入口（建议也跟随系统偏好并记忆选择）。技术要点：现有配色散落在 CSS 与 Canvas `draw()` 硬编码色值中，需先**颜色变量化/主题化**（CSS 变量 + Canvas 配色表），再做亮色设计稿；属纯前端重构，不依赖后端。 | 前端样式层（CSS + Canvas 绘制） | 无（可独立迭代，宜与 #7/#3 动效组件一起做） |

## 二、优先级建议（P0 近期 / P1 平台期 / P2 生态期）

判定维度：用户价值、成本、是否阻塞后续、风险。

| 原# | 功能 | 建议 | 一句话理由 |
|-----|------|------|-----------|
| 7 | 吃子特效优化 | **P0** | 纯前端、成本可控、视觉感知最强，先做"第一眼" |
| 3 | 新手教程 | **P0** | 决定首次上手留存；与 #7 可共用动效组件 |
| 1 | 悔棋 | **P0**（本地/人机）/ **P1**（在线确认制） | 玩法高频诉求；在线部分需协议设计，留到平台期 |
| 8 | 自定义头像昵称 | P0 本地版 → P1 云端版 | 小投入高个性价值，先本地、账号化后升云端 |
| 9 | 登录 + 游客 | **P1** | 身份地基：管理、历史归属、云端资料都依赖它 |
| 10 | 数据库持久化 | **P1** | 数据地基：历史/回放/账号落库的前提 |
| 5 | 历史记录 | **P1** | 与 #6 一起设计；依赖 #10 |
| 6 | 回放 | **P1** | 与 #5 共用记录格式；复用前端动画 |
| 2 | 第三方旁观 | **P2** | 属生态增强；需要房间入口与广播升级 |
| 4 | 管理员功能 | **P2** | 运营向；需 #9+#2+#10 齐备后价值才完整 |
| 11 | 亮 / 暗双主题 | **P1**（可与 M1 的设置面板同批做） | 纯前端、无后端依赖，但需先把硬编码颜色主题化，改动面适中 |

> 小结：**先做三个高感知低风险项（7/3/1）快速见效，再集中做"账号+数据库"平台化（9/10/5/6/8 云端），最后上观战与管理（2/4）。**

## 三、分期路线（建议）

| 阶段 | 版本 | 目标 | 包含 |
|------|------|------|------|
| M1 | v1.2（纯前端） | 上手体验升级 | #7 特效、#3 新手教程、#1 悔棋（本地/人机）、#8 本地昵称头像、#11 主题切换（亮/暗） |
| M2 | v2.0（平台化） | 账号 + 数据打通 | #9 登录/游客、#10 数据库、#8 云端化、#5 历史记录、#6 回放 |
| M3 | v2.x（在线生态） | 观战与运营能力 | #2 旁观、#4 管理员、房间列表/邀请等扩展项 |

每阶段结束可发版并回归；进入某条开发前，再从本文档拆出正式需求（沿用 ProductRequirements / GameDesign / TechnicalSpec 文档流程）。

## 四、拓展功能建议（在 10 条之外的加分项）

| 建议项 | 理由 / 说明 | 建议档 |
|--------|-------------|--------|
| 房间目录与邀请链接 | #2 旁观与找人下棋都需要入口；低成本高传播 | 随 #2 |
| 断线重连与对局恢复 | 在线体验重要短板；利用 #10 保存对局状态 | M2 后可做 |
| 对局计时（步时/总时/超时判负） | 回合制策略的标配，防挂机 | M2 |
| 认输/和棋（提议）机制 | 补全对局结束方式，规则文档需同步 | M2 |
| 观战延迟 + 防作弊校验 | 防止观战者通风报信；服务端校验落子 | 随 #2 |
| 观战互动（表情/加油、聊天分房间） | 提升直播观感，非必须 | P2 之后 |
| Elo 积分 / 段位 / 战绩页 | 让"在线对战"有成长目标，留存利器 | M3 |
| AI 难度分档 + 自对弈棋谱 | 现有 AI 只有一档；自对弈可为 #6 生成素材 | M3 |
| 每日残局 / 挑战 | 轻内容运营，低成本日活抓手 | 随时可插 |
| 设置面板（音效 / 更多棋盘皮肤 / 减少动效） | 体验完整性；亮/暗主题见 #11，设置面板与 #7 动效开关一起做 | P0 收尾 |
| 无障碍与移动端触控细节 | 键盘操作、色弱棋盘配色、触屏手感 | 贯穿各期 |

> 以上均未承诺开发，仅作为后续规划素材；如需加入正式清单，直接在此表前加一行并标优先级即可。

## 五、维护约定

- 优先级是**建议**，最终取舍以产品决策为准。
